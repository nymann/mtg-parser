final plan

Agentic grammar flow for long-term parser quality.

Replace the card-first repair loop with a staged professional grammar workflow: concept first, evidence second, AST before grammar, patch only after an approved path, and score grammar debt after the patch.

Optimize for grammar health A parsing card is necessary, but not sufficient.
Make new rules expensive Widening or refactoring must be the shortest approved path.
Separate design from patching The agent that chooses the path does not get to quietly override it while coding.
Expose human-level steps The UI should show progress through the same steps a reviewer would use.

Problem

The existing add-card flow asks an agent to make the next failing card parse. That is too local. Recent commits show the result: many successful one-card patches, many new pest rules, and repeated growth in the same grammar core files. The failure is not that the agent cannot solve cards. The failure is that the workflow rewards the quickest local parse instead of durable grammar design.

Final direction: treat each card as evidence for a reusable grammar capability. The workflow may throw away most of the current card loop. What must remain is the professional sequence: understand concept, find neighbours, choose path, design AST, implement, test, audit debt.

System Shape

The new flow has three agents or phases with hard boundaries. This is how we avoid asking one agent to both make the design decision and satisfy implementation pressure.

Concept Agent

Classifies the missing capability and explains the Magic concept. It is read-only and cannot edit files.

Decision Gate

Deterministic code scores the concept decision against neighbours, history, grammar audit, and debt thresholds.

Patch Agent

Implements only the approved recipe. If the recipe is wrong, it stops with RECIPE_BLOCKED.

End-To-End Flow

This is the orchestration shape. Blue nodes are deterministic tool work, violet nodes are agent prompts, gold nodes are deterministic gates, green nodes are successful outcomes, and red nodes are blocked or redirected outcomes.

Card Intake tool

Load card, Oracle text, parse failure, focused generated failure, and corpus status.

Concept Prompt agent

Classify the missing reusable Magic concept. No code edits.

Neighbour Search tool

Find grammar, AST, parse, unparse, semantic, corpus, rules, and commit-history neighbours.

Decision Prompt agent

Choose existing, widen, refactor, new reusable rule, tooling, or human design.

Decision Gate gate

Reject unproved new rules, weak neighbours, card-specific concepts, or high-debt paths.

AST Prompt agent

Design the AST contract and examples before grammar syntax changes.

Recipe Gate gate

Render a scoped recipe only if concept, decision, and AST plan are approved.

Patch Prompt agent

Implement only the approved recipe or return RECIPE_BLOCKED.

Run focused, neighbour, property, semantic, corpus, and grammar audit gates.

Debt Gate gate

Compare actual diff to budget and score grammar debt.

Commit outcome

Commit low-debt green capability patches.

Route high-debt or blocked runs to refactor, tooling, or human design.

Grammar Access Strategy

The agent should not be handed the full growing grammar.pest file. That makes it slow, encourages local string hacking, and hides the structure we want it to reason about. Treat the pest grammar the same way we treat the Comprehensive Rules: expose a query tool and curated slices.

Phase 1: Virtual Split

Keep the physical grammar.pest file unchanged, but build an index of top-level rules, dependencies, reverse dependencies, literal words, rule-name tokens, and section headers.

Phase 2: Agent Slices

Prompts include only relevant rule slices and linked AST/parse/unparse surfaces. Agents can request more slices through grammar_query, not by reading the whole file.

Phase 3: Physical Split

Only after the virtual modules are stable, consider real source fragments. If pest cannot consume fragments directly, generate the single grammar.pest deterministically from fragments.

Recommendation: do not start with a physical split. Start with grammar_query. It gives immediate prompt quality benefits, avoids pest build-system risk, and creates data that tells us where real module boundaries should be.

PEST Query Tool

grammar_query is the local equivalent of a rules search tool. It answers questions about our grammar instead of the Comprehensive Rules.

Query Shape Example Returns
rule:<name> rule:damage_recipient Rule body, line range, dependencies, reverse dependencies, nearby comments.
lex:<words> lex: prevent damage source recipient Rules whose literal words or rule-name tokens overlap the query.
uses:<rule> uses:source_object Every rule that references the named rule, grouped by domain slice.
neighbours:<rule> neighbours:static_damage_prevention_effect Rules with similar RHS skeletons and duplicated quantity/target/duration shapes.
domain:<tag> domain:damage Curated or inferred domain slice: top-level effects, helper rules, AST/parser links.
edit-scope:<rule> edit-scope:damage_recipient Editable rule block plus read-only dependents and validation commands. 
grammar_query("lex: prevent damage source recipient")
  -> matches:
     static_damage_prevention_effect       lines 1499-1508
     source_object_damage_recipient        lines ...
     damage_prevention_amount_axis         lines ...
  -> related source:
     ast.rs: Effect::PreventDamage
     parse.rs: parse_prevention_effect
     unparse.rs: unparse_prevention_effect
  -> warnings:
     "recipient axis appears duplicated in 3 rules"

Physical Grammar Split

Splitting the file may still be right, but it should be a later refactor with evidence. The virtual index can tell us which modules are real instead of guessing.

Option Pros Risks When To Use
Keep one file, query slices No parser build change, immediate agent improvement, easy rollback. Humans still see one large file in normal editing. First implementation.
Generated single grammar from fragments Humans and agents edit modules, pest still receives one generated grammar. Requires deterministic generator and clear generated-file ownership. After virtual domains stabilize.
Native multi-file pest input No generated grammar file if supported cleanly by the local pest version. Needs verification against pest_derive, editor tooling, and existing xtask assumptions. Only after a small spike proves it compiles and tooling adapts.

Prompt And Sequence Diagrams

These diagrams show the expected conversation. The key pattern is that the orchestrator gathers evidence, prompts for a narrow structured decision, validates that decision, and only then allows implementation.

1. Concept Classification

Orchestrator -> Tools:
  parse_probe(card.oracle)
  rules_search(query) only if rules-heavy

Orchestrator -> ConceptAgent:
  "Classify the missing reusable grammar concept.
   You may not propose code. Return CONCEPT_CLASSIFICATION."

ConceptAgent -> Orchestrator:
  CONCEPT_CLASSIFICATION
  - kind
  - surface_text
  - reusable_capability
  - why_not_card_specific
  - rules_questions

Orchestrator -> Gate:
  reject if concept is card-named,
  too broad, or unsupported by the text.

2. Neighbour Evidence

Orchestrator -> Tools:
  grammar_query("lex: concept words")
  grammar_search(concept words)
  grammar_neighbours(failing span)
  corpus_examples(signature)
  history_scan(signature)

Orchestrator -> ConceptAgent:
  "Review these neighbours. Which existing rules
   are relevant and which axis differs?"

ConceptAgent -> Orchestrator:
  NEIGHBOUR_REVIEW
  - closest_rules
  - reusable_axes
  - examples_to_preserve
  - counterexamples
  - missing_evidence_requests

3. Implementation Decision

Orchestrator -> DecisionAgent:
  "Choose exactly one path in this order:
   already covered, widen, refactor, new reusable rule,
   tooling, human design. Reject earlier paths with evidence."

DecisionAgent -> Orchestrator:
  IMPLEMENTATION_DECISION
  - chosen
  - existing_rule
  - axis_to_add
  - new_rule_needed
  - rejected_options
  - change_budget

Orchestrator -> Gate:
  fail if new_rule_needed lacks proof,
  budget is too large, or neighbours are weak.

4. AST Design

Orchestrator -> Tools:
  ast_surface_map(concept)
  grammar_search(existing AST neighbours)

Orchestrator -> AstAgent:
  "Design the AST contract before grammar syntax.
   Preserve all semantic axes needed for round-trip
   and lowering."

AstAgent -> Orchestrator:
  AST_PLAN
  - variant_or_existing_variant
  - fields
  - examples
  - counterexamples
  - lowering_expectation

Orchestrator -> Gate:
  reject if AST cannot represent examples
  or collapses meaningful distinctions.

5. Patch Recipe

Orchestrator -> Tools:
  recipe_render(decision, ast_plan)
  grammar_slice(approved_edit_rules)

Orchestrator -> PatchAgent:
  "Implement this exact recipe.
   Do not change the approved path.
   If the path is impossible, return RECIPE_BLOCKED."

PatchAgent -> Orchestrator:
  PATCH_REPORT
  - diff
  - GENERALIZATION_PATH
  - pest rules added/widened/removed
  - AST/parse/unparse/lower touched
  or RECIPE_BLOCKED

Orchestrator -> Gate:
  reject if actual changes exceed budget
  or forbidden files changed.

6. Validation And Debt

Orchestrator -> Tools:
  validation_run(recipe)
  grammar_audit(diff)
  debt_score(diff, budget)

Tools -> Orchestrator:
  VALIDATION_RESULT
  DEBT_AUDIT

Orchestrator:
  if tests pass and debt low: commit
  if tests pass and debt medium: review/refactor follow-up
  if tests fail: classified repair recipe
  if debt high: redirect, no commit

Decision Order

This order encodes the incentive. New grammar is allowed, but it is not the default cheap answer. 

1. existing rule already covers it
2. widen existing rule
3. refactor or merge duplicated existing rules
4. add a new reusable rule
5. card-shaped rule: forbidden unless human-approved

The agent must reject earlier options with evidence before choosing a later option. A new rule without this rejection proof is not an implementation path; it is a blocked recipe.

Grammar Debt Score

The patch is judged after tests. A passing card with high debt is not automatically accepted. 

debt =
  new_pest_rules * 3
  + card_named_rule_penalty
  + duplicate_rhs_penalty
  + path_d_penalty
  + budget_overrun_penalty
  + corpus_regression_penalty
  - old_rules_removed * 2
  - generalized_rules_widened
  - cards_unlocked * 2
Debt Result Meaning Action
Low Patch fits budget, tests pass, no obvious drift. Commit.
Medium Patch passes but adds more surface than expected or touches risky neighbours. Require review or generate refactor follow-up before more cards.
High Patch is card-shaped, duplicates grammar, exceeds budget, or declares path d without proof. Do not commit without human approval. Prefer refactor-first.

Fast But Good

The flow should still be fast. The trick is to make the good path the shortest approved path.

Low-Risk Widening

If neighbours are clear and budget is zero new pest rules, the flow can move quickly from decision to patch.

High-Debt Choices Slow Down

New top-level rules, card-like names, duplicated RHS, and path d trigger review or refactor recipes.

Refactor Is Success

An outcome of refactor_needed is not failure. It is the system choosing grammar health before more card support.

Implementation Plan

  1. Define artifacts: add schemas for concept.json, neighbours.json, implementation_decision.json, ast_plan.json, patch_report.json, validation.json, debt_audit.json, and outcome.json.
  2. Add grammar index: implement grammar_query and grammar_slice over the existing single grammar.pest file before any physical split.
  3. Add read-only design command: implement cargo xtask add-card-design --card <id> that runs steps 1-4 and stops before patching.
  4. Add deterministic gates: reject concept/card-name coupling, missing neighbour analysis, unproved new-rule decisions, and AST plans that lose semantic axes.
  5. Add recipe renderer: render a patch recipe only from an approved implementation decision and AST plan.
  6. Add patch bridge: run the patch agent with the recipe. The agent can only patch or return RECIPE_BLOCKED.
  7. Add validation runner: run focused, neighbour, tier 2, semantic, corpus, and grammar audit gates.
  8. Add debt audit: compare actual diff to budget and score grammar debt.
  9. Add commit/redirect logic: commit low-debt green patches; otherwise produce the next recipe and leave the working tree/logs inspectable.
  10. Build UI on reviewer steps: show one progress row per reviewer step, with artifacts, current gate, and decision reason visible.
